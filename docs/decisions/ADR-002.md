# ADR-002: 采用 GitHub Pages 托管，push 即发布

## Status
Accepted (2026-10-26)

## Background
项目需要一个公开、可分享、长期稳定的体验链接交给评委。同时开发者本机的网络环境存在一个硬约束：到 `github.com:443` 的连接被代理拦截（`CONNECT tunnel failed, response 502`），而 `api.github.com` 与 `ssh.github.com:443` 通路正常。这决定了「用什么托管」和「怎么把代码推上去」两件事必须一起考虑。

## Decision
1. **托管平台选 GitHub Pages**，产物根目录就是仓库里的 `src/`，通过 GitHub Actions 自动发布（`.github/workflows/deploy.yml`）。
2. **推送方式用 GitHub Git Database API**（建 blob → tree → commit → ref），而不是 `git push` 或 SSH。

## Consequences

**正面**
- Pages 与仓库同源：`#/r/owner/repo` 深链既能分享报告，也能一眼看到源码，与「算法完全公开」的产品主张一致
- 无构建：`src/` 直接交给 `upload-pages-artifact`，从 commit 到线上只隔一个 job
- Hash 路由 + 全相对路径：部署在 `gztcode.github.io/code-icu/` 子目录下零配置，不需要服务端 rewrite 规则
- `src/.nojekyll`：显式关闭 Jekyll 处理，杜绝未来新增 `_` 开头目录时被吞掉
- 发布后自动冒烟：workflow 的第二个 job 校验 19 个关键静态资源与首页内容，失败只告警不阻塞发布

**负面**
- Pages 没有服务端，无法做 SSR、无法写 cookie 鉴权，与本项目「无后端」定位一致，但后续若要加埋点统计需换方案
- GitHub Pages 有构建产物大小与流量限制（软性），当前 `src/` 仅 328K，无风险
- **本机 `git push` 到 GitHub 不可用**：SSH 公钥因 `gh` token 缺 `admin:public_key` scope 未能上传，HTTPS 直连被代理拦截。当前推送靠 API 脚本完成；后续若要恢复标准 `git push`，需执行 `gh auth refresh -s admin:public_key` 后把公钥加到账号，并配置 `~/.ssh/config` 将 `github.com` 指向 `ssh.github.com:443`（端口 443 已在 `known_hosts` 中登记）

## Alternatives Considered

| 方案 | 否决原因 |
|---|---|
| WorkBuddy 托管（`workbuddy_sites_deploy`） | 能用，但站点与账号绑定、无法沉淀为公开仓库；比赛作品需要可被评委独立访问的稳定地址 |
| Vercel / Netlify | 需要接入第三方账号与构建配置；且与「源码即产物」的原则相比没有额外收益 |
| `gh-pages` 分支手工发布 | 每次发布多一步 git 操作，容易漏；Actions 自动发布更省心，且天然带发布记录 |
| 直接把 `src/` 挪到仓库根 | 会打乱「源码目录 / 测试 / 设计稿」的分区，可读性变差；Pages 完全支持指定子目录发布 |
