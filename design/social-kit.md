### 2.2 知乎（问题式标题、有论证、可长）

**主标题**：`如何判断一个开源项目是不是已经死了？`
**备选 A**：`一个 npm 包废弃六年了，为什么还装在你的项目里？`
**备选 B**：`给 GitHub 仓库算健康分，这件事有意义吗？`

正文（约 1250 字）：

```
先说结论：看"最后一次提交时间"是不够的，但看"六项可量化的体征"，够用。

## 一、为什么 last commit 不是好指标

接手老项目之前我会先翻仓库，最常见的一步是看最后提交时间。这一步经常骗人。

有的项目一年提交几百次、几十个人在推，但 issue 积压到四位数没人管；
有的项目一年只提交 3 次，但每次都修同一个安全边界，稳定运行五年。

前者是"看起来活着"，后者是"看起来死了"。last commit 分不出这两种。

## 二、拆成六项

我把仓库当病人，查六项，每项 0-100 分：

心跳：距最后一次提交多久。7 天内满分，之后按天分档往下扣，超过一年只剩 30 分以下，两年归零。
呼吸：近 12 个月的提交密度，再加一层"最近半年 vs 前半年"的趋势修正。
依赖度：近 12 个月提交里，占比最高的那个人占多少。这类指标一般叫 bus factor。
代谢：距最近一次发版多久。30 天内满分，两年没版本只剩 15 分。
免疫：未关闭 issue 里，挂了 90 天以上没人动的比例，再按积压总量分级扣分。
遗嘱：许可证 + README 的完整度（是否过一千五百字、有没有安装段/使用段/许可段/状态徽章）。

加权：心跳 25%、呼吸 20%、依赖度 20%、免疫 15%、代谢 10%、遗嘱 10%，总分 0-100，按五档分诊。

## 三、呼吸为什么给到 20%

因为提交频率的衰减是整个模型里最早的预警信号。

一个项目通常先"少提交"，再"不提交"，最后才"不发版"。发版可以靠 CI 代劳，issue 数可以靠沉默维持，只有提交节奏是人手决定的。所以我给它第二高的权重，比免疫和代谢都高。

## 四、它也会给高分

这是我最想说的一点。

如果只看"死掉的项目"，任何工具都能伪装成洞察。真正能说明模型有效的是反例。

我用它跑 express：87 分，健康。
近 12 个月 96 次提交，43 个不同作者，单人最高占比 11.9%，最新版本 v5.3.0 发布于 2026 年 10 月 10 日。

这是一个 Node 生态里被长期使用的框架，而且它确实还在正常运转。工具给出的结论和事实一致。

再跑 moment：69 分，住院观察。仍在维护，但免疫一项只有 23.2 分——60 个未关闭 issue 里，大部分挂了很久没人动。

最后跑 request：16 分，临床死亡。803 天无提交，README 第一行写着 Deprecated，作者 2020 年 2 月 11 日就宣布废弃了。

同一套标准，三个结局。这才说明分数是有区分度的。

## 五、局限

说清楚边界，比吹功能重要：

它不评代码质量。不做复杂度分析、不看重复率——那要拉全量源码，请求量和体积都不可控。
它不扫 CVE。没有接 OSV 之类的漏洞库。
它只看公开数据。单次体检固定 5 次 GitHub REST 请求，不登录可用，所以拿不到"某次提交改了什么"这种深信息。
寿命推演那栏是公式算出来的剩余天数，不是预言——页面上就写着"不是算命"。

## 六、所以它有什么用

三个具体场景：选型前看一眼、接盘前看一眼、给自己的项目做一次体检查漏。

工具叫 Code ICU，1024 程序员节做的作品，纯前端、无账号、不需要登录。

地址在评论区。配图是我做的六项体征速查图，一屏能看完到底查了什么。

#WorkBuddy #1024程序员节
```

配图：**图 3（六项体征速查 1080×1350）**，放回答开头。

发布要点：
- 优先在已有高热度问题下写回答，不要新开问题。搜索"开源项目 维护""依赖 废弃""bus factor"找相关问题。
- 第一段必须是结论，知乎的折叠线在第三行。
- 标签同样要带 `#WorkBuddy #1024程序员节`。

## 5. 人气分的真实目标：稳过 61

评审只认点赞 + 收藏之和，四档分值是：

| 累计 | 得分 | 与上一档的边际收益 |
|---|---|---|
| ≥10 | +5 | — |
| ≥31 | +10 | +5 |
| **≥61** | **+15** | **+5** |
| ≥101 | +20 | +5 |

**关键在于：从 61 到 101 要多攒 40 个赞，只多 5 分。** 这 40 个赞的成本，远高于从"完成度"或"使用体验"里抠 5 分的成本。所以策略是：

```
目标 = 稳定过 61（拿到 +15）
不追 101（那 5 分性价比太低）
如果自然冲到 85+，再顺手推一把
```

| 阶段 | 目标累计 | 主要来源 | 若进度落后的补救 |
|---|---|---|---|
| 10/30 24:00 | 30（差 1 就够 +10） | 朋友圈 + 3 个技术群 | 追加一个群；请互关好友先收藏 |
| 10/31 24:00 | 45–50 | 知乎长尾 + 小红书二帖 | 在知乎回答下回复每一条评论（提升推荐权重）；小红书换图 2 重发一次 |
| 11/01 20:00 | **61+** | 一对一私聊 + 收尾帖 | 私聊名单从 10 人扩到 20 人，只发图 2 不写长文 |
| 11/01 23:59 后 | — | — | 停止一切拉票。数据已封，别浪费人情 |

**一句实话**：61 不是爆款线，是熟人圈够得到的位置——十几个同事、几个技术群、发小和同行，就够了。私聊是必要动作，不用不好意思，但话要说明白："评审按点赞 + 收藏之和算，如果你觉得这个工具有点意思，收藏一下就行，不用转发。" 不要用"求支持""帮忙冲一冲"这类无信息量的话，也不要在群里刷屏。

**别做的三件事**：不买赞、不建互赞群、不承诺回赞。评审细则里"互动数据真实有效"这条，一旦被判定异常，扣的比 +15 多得多。

## 6. 合规自查（逐条对照评审禁止项）

| 评审禁止项 | 我们的情况 | 物料里的执行约束 |
|---|---|---|
| **算命占卜类内容** | 不触线。所有输出是确定性公式的结果：同一仓库同一时刻算两次结果完全一致，没有随机数、没有出生时间、没有星盘。分诊是**按分数区间命名**（0-29 临床死亡），不是"运势" | 文案里出现"病危通知书"这种医疗隐喻时，**必须同时出现"不是算命/不是预言"**（三套文案均已埋）；禁用"算命""运势""吉凶""玄学""占卜"作卖点；图 3 底部固定一行"不是算命" |
| **虚假信息 / 夸大宣传** | 只引用事实池；每条都能在 GitHub 页面上核对到 | 禁用"最强 / 第一 / 颠覆 / 唯一 / 神器 / 秒杀"；不写 npm 下载量；不写"停止维护"（仓库未归档，准确说法是"作者宣布废弃"）；不猜测废弃原因；不评价维护者个人 |
| **侵犯他人权益** | 使用公开事实数据（star 数、提交数、issue 数、许可证），不复制他人作品性表达 | 不使用 GitHub Logo 或任何商标；不使用仓库官方头像/插图（Canvas 已规定不绘制远程头像，用首字母色块）；README 只引用一行 `Deprecated!` 并标明出处，不做长段转载；不 P 图篡改仓库页面截图 |
| **未脱敏的个人隐私** | 产品零采集：无账号、无埋点、无 cookie，仓库地址不上传任何服务器 | 截图前裁掉浏览器书签栏、账号头像、通知角标；文案不出现任何真实姓名、公司名、邮箱、聊天记录 |
| **未公开的第三方数据** | 不使用 | 禁止出现 npm 周下载量、SimilarWeb 类流量、"某公司内部统计"；示例只用事实池里的 4 个仓库 |

## 7. 评论区应对话术（被质疑时的标准回答）

评审会看评论区，围观者也会。预备四条：

**Q：这不就是看 last commit 吗？**
> 不是。六项里心跳只占 25%，而且我们专门给了呼吸（提交密度 + 前后半年趋势）20%、免疫（僵尸 issue 占比）15%。express 的 last commit 是 2 天前，但它的免疫只有 40.6 分——只看看 last commit 的话，这一项看不出来。

**Q：给项目打这种分，是不是在唱衰开源？**
> 这套分也能打高分。express 87 分健康，我们把它放在首页当第一个示例，就是为了说明绿色是真能亮起来的。分数低的那几个，问题都写在报告里，每条都能点开看怎么算的。

**Q：16 分是不是故意挑的极端案例？**
> request 不是编的案例：803 天没提交、README 第一行写着 Deprecated、145 个 issue 挂着，每条都能在 GitHub 上核对。它确实是我们挑出来当主推的，因为它的问题最清楚。但同一套算法跑 express 是 87、跑 moment 是 69，分布是连续的，不是只挑最惨的那一个。

**Q：数据可信吗？**
> 全部来自 GitHub 公开 REST API，页面顶部标注了抓取时间和请求路径。算法公开，权重公开，你可以自己拿 API 复算一遍。
